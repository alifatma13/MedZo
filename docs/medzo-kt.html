MedZo — Engineering Knowledge Transfer

Complete system design, architecture decisions, content patterns, accessibility standards, and operational guide for the MedZo marketing website.

Domain: medzo.com.au Stack: Astro 6 + Sanity + TypeScript Hosting: Hostinger (static) CMS: medzo.sanity.studio Node: ≥22.12.0

Project Overview

MedZo is a static marketing website for an Australian medical practice management software product. It is built with Astro's static site generation for maximum performance and SEO, driven by Sanity as a headless CMS for all team-managed content, and deployed automatically to Netlify on every push to main.

The project's primary architectural goal is long-term maintainability: any visible word on the site can be changed by editing only src/lib/content/ or via Sanity Studio — no component rewrites required.

ℹ️
Core principle: If a change requires touching more than two files to update a single piece of copy, the architecture is wrong — fix the structure, not the symptom.

Content Management Strategy

MedZo uses a dual content system. The split is based on who owns the content and how often it changes:

Sanity CMS

Team-managed content that changes frequently. Edited via Sanity Studio. Fetched at build time via GROQ queries. Requires a Netlify redeploy to go live.

  • Home, About, Contact, FAQ page content
  • Services collection (dynamic route)
  • Team members, Testimonials
  • Site settings (navigation, footer tagline, social links)
src/lib/content/

Developer-managed static content that rarely changes. Edited in code; deploy on push to main.

  • Navigation ARIA strings & branding
  • Footer column headings & legal links
  • Privacy policy & Terms of service (full text)
  • 404 page text
  • JSON-LD schema builders
  • Form labels & validation error messages
  • Shared UI labels & ARIA strings

Fetcher Pattern

Every data type has a dedicated fetcher file in src/lib/api/. The pattern is consistent across all fetchers:

// src/lib/api/homePage.ts
import { defineQuery } from "groq";
import { sanityClient } from "./sanity";

// 1. Define typed GROQ query
export const HOME_PAGE_QUERY = defineQuery(`
  *[_type == "homePage"][0]{
    hero { heading, subheading, ctaPrimary, ctaSecondary },
    ticker,
    howItWorks { steps[] { ... } }
  }
`);

// 2. Export async fetcher
export async function getHomePage() {
  return sanityClient.fetch(HOME_PAGE_QUERY);
}

SVG Icon Registry

All SVG icons live in src/lib/utils/icons.ts as a keyed string map. No inline SVG is permitted in component templates.

Usage Pattern

// In any .astro component
import { icons } from "../lib/utils/icons";

// Template — renders the SVG string safely
<Fragment set:html={icons["calendar"]} />

Adding a New Icon

Step 1 — Get the SVG source

Copy the raw SVG markup from your source (e.g. Heroicons, Lucide, Phosphor, or a custom export from Figma). Strip any outer <?xml> declaration and any wrapping <html>/<body> tags — keep only the <svg> element and its children.

Step 2 — Clean the SVG

  • Remove any hardcoded fill or stroke colour attributes (e.g. fill="#000000") so the icon inherits currentColor from CSS.
  • Replace them with fill="currentColor" or stroke="currentColor" as appropriate.
  • Remove width and height attributes if present — size is controlled by CSS on the parent element.
  • Make sure a viewBox attribute is present (e.g. viewBox="0 0 24 24").
  • Add aria-hidden="true" to the <svg> tag — icons are decorative; accessible labels belong on the parent button or link.

Step 3 — Add it to the registry

Open src/lib/utils/icons.ts and add the new entry to the icons map. Use a kebab-case key that describes what the icon looks like, not where it's used. 

// src/lib/utils/icons.ts
export const icons: Record<string, string> = {
  // ... existing icons ...

  "my-icon": `<svg viewBox="0 0 24 24" fill="none" stroke="currentColor"
    stroke-width="2" aria-hidden="true">
    <path d="M5 12h14M12 5l7 7-7 7"/>
  </svg>`,
};

Step 4 — Use it in a component

import { icons } from "../../lib/utils/icons";

<!-- Renders the SVG string safely, no XSS risk from internal registry -->
<Fragment set:html={icons["my-icon"]} />
⚠️
Never paste an inline <svg> block directly into a component template. All icons must go through the registry. This keeps icons in one place, makes them reusable, and means any icon can be updated site-wide by editing a single line in icons.ts.

Accessibility

✅
Baseline: WCAG 2.1 AA. Every violation is treated as a bug, not a nice-to-have.

Semantic HTML

  • ✓Correct elements: <button> for actions, <a> for navigation, landmark elements throughout.
  • ✓Sequential heading levels (h1 → h2 → h3). Never skip a level for visual style — use CSS instead.
  • ✓Every page has exactly one <h1>.
  • ✓Landmark regions: <nav>, <main>, <header>, <footer>, <section>, <article>.

Keyboard & Focus

  • ✓All interactive elements reachable by keyboard alone (Tab, Shift+Tab, Enter, Space).
  • ✓Visible :focus-visible ring on all interactive elements. Never removes default outline without replacing it.
  • ✓Mobile nav drawer traps focus while open; returns focus to trigger on close.
  • ✓Skip-to-content link in Layout.astro — first focusable element on every page.
  • ✓No tabindex greater than 0.

ARIA Patterns

  • ✓FAQ accordion: button[aria-expanded], [aria-controls], role="region" on panel.
  • ✓Nav drawer: role="dialog", aria-modal="true", aria-label from content file.
  • ✓Carousel controls: aria-label on prev/next buttons from ui.ts.
  • ✓All ARIA strings come from src/lib/content/ — never hardcoded in templates.
  • ✓Prefer native HTML semantics over ARIA roles. Only add ARIA when native is insufficient.

Images & Media

  • ✓Astro <Image /> component used for all raster images (never raw <img>). Auto-optimises and requires alt.
  • ✓Meaningful alt text on all images. Decorative images: alt="".
  • ✓Sanity images use urlFor() with explicit width/height for proper intrinsic sizing.

Forms

  • ✓Every input has an associated <label> via for/id.
  • ✓Error messages programmatically associated via aria-describedby.
  • ✓Required fields marked with aria-required="true".
  • ✓All form labels come from src/lib/content/contact.ts — typed and stable.

Colour & Contrast

  • ✓Body text: minimum 4.5:1 contrast ratio.
  • ✓Large text (≥18pt) and UI components: minimum 3:1.
  • !Run a contrast checker before shipping any new colour combination.

Pre-commit Accessibility Checklist

  • ✓Keyboard-navigate full page — no traps, no unreachable elements.
  • ✓Run Axe or Lighthouse — zero critical or serious violations.
  • ✓Test with NVDA or VoiceOver on the main user flow.
  • ✓All images have appropriate alt text.
  • ✓Colour contrast checked for any new palette entries.

Animations

All animations use the motion package (framework-agnostic Framer Motion). Raw CSS @keyframes are not used for anything beyond the simplest static transitions.

Required Script Wrapper

🚨
Every <script> block must wrap all code in astro:page-load. The site uses ClientRouter for SPA-style navigation. Without this wrapper, animations only fire on the first page load and are invisible on every subsequent navigation. 
document.addEventListener("astro:page-load", () => {
  if (!window.matchMedia("(prefers-reduced-motion: reduce)").matches) {
    // All animate / inView / RAF calls go here
  }
});

No-Flash Rule

Never animate from opacity: 0 in JS without first setting opacity: 0 in CSS. Otherwise the browser paints the element visible on frame zero, then the animation snaps it to invisible — causing a visible flash. 

/* CSS — inside the component's <style> block */
@media (prefers-reduced-motion: no-preference) {
  .hero-heading, .card { opacity: 0; }
}

/* JS — animate from the CSS initial state */
(animate as any)(
  ".hero-heading",
  { opacity: [0, 1], y: [24, 0] },
  { duration: 0.5, easing: [0.22, 1, 0.36, 1] },
);

Required Animation Patterns

PatternAPIDurationWhen to use
Entrance (above fold) animate() 0.4 – 0.7s Every above-the-fold section on load
Scroll reveal inView() 0.4 – 0.6s Sections below the fold as they enter viewport
Staggered lists stagger(0.08) 0.4 – 0.5s Any list of cards or items
Button hover animate(scale: 1.04) 0.15s All CTA buttons
Page transition animate(opacity: [0,1]) 0.35s On every route change (ClientRouter)

RAF Loops (Canvas / Ticker)

let rafId: number | null = null;

document.addEventListener("astro:page-load", () => {
  if (rafId !== null) {
    cancelAnimationFrame(rafId);   // prevent duplicate loops on nav
    rafId = null;
  }
  rafId = requestAnimationFrame(draw);
});

Motion TypeScript Cast

The motion package's TypeScript overloads don't cover all valid runtime calls (CSS selector strings, y shorthand, etc.). Use the cast pattern instead of @ts-ignore: 

// Correct — cast suppresses overload error on the entire call
(animate as any)(".selector", { opacity: [0, 1], y: [24, 0] }, { duration: 0.5 });

// Wrong — @ts-ignore only suppresses the line it's on
// @ts-ignore
animate(".selector", { opacity: [0, 1] }, { duration: 0.5 });

Animation Rules Summary

  • ✓Prefer spring or custom cubic-bezier easing over linear.
  • ✓Entrance: 0.4–0.7s. Micro-interactions: 0.1–0.2s.
  • ✓Always respect prefers-reduced-motion — wrap all animate calls.
  • ✓Only animate transform and opacity — not layout properties (width, top, etc.).
  • !Never animate from opacity: 0 in JS without matching CSS opacity: 0.
  • !Never place animate/inView calls at the top level of a script block.
  • !Never attach event listeners outside astro:page-load.

No-Hardcoding Rule

Every piece of content in a component template must come from an external source. No exceptions.

Content TypeWhere it livesHow to use it
Text, labels, ARIA strings, hrefs src/lib/content/*.ts Export typed object; import and pass as props
SVG icons src/lib/utils/icons.ts icons["key"] → <Fragment set:html={...} />
Raster images (PNG, JPG, WebP) src/res/ or Sanity CDN Import the file or use urlFor(); pass via typed prop
CMS content (team, services, etc.) Sanity Studio Fetch via src/lib/api/*.ts; pass as props

Violations to Catch Before Committing

  • !A bare string inside a template tag: <h2>Our Services</h2> — move to a content file.
  • !An inline <svg> block in a component — move to icons.ts.
  • !A hardcoded src="..." on an <Image /> — import from src/res/ or use urlFor().
  • !A hardcoded href, aria-label, or alt containing real copy — move to a content file.
  • !Em-dashes (—) in copy — use a comma, colon, or rephrase instead.
ℹ️
The test: If you can change any visible word or icon on the page by editing only files in src/lib/, src/res/, or Sanity Studio, the component is clean.

Sanity — SEO

Every page on the site outputs a full set of SEO tags — page title, meta description, canonical URL, Open Graph, Twitter Card, and JSON-LD structured data — all driven by src/layouts/Layout.astro. Some fields are editable in Sanity; others are handled automatically or require a developer to change.

How it works

Pages pass title and description props to <Layout />. Layout uses these to populate every meta tag in <head>. If a page does not pass these props, Layout falls back to the global defaults defined in src/lib/content/site.ts. 

<!-- Every page passes its SEO values like this -->
<Layout
  title={page.seoTitle ?? undefined}
  description={page.seoDescription ?? undefined}
>

Sanity — Making a Content Change

⚠️
Publishing in Sanity Studio does NOT update the live website automatically.

The live site at medzo.com.au is a set of static HTML files sitting on Hostinger. It was generated the last time someone ran npm run build. It has no connection to Sanity after that build — it does not check for new content, it does not update on publish, and it has no awareness that Sanity even exists at runtime.

When you publish a change in Sanity Studio, the live site will continue showing the old content until a developer rebuilds the site and re-uploads it to Hostinger. There is currently no automated pipeline to do this — it is always a manual step.

Why does this happen?

Astro builds the site statically — at build time it fetches all content from Sanity, converts it into plain HTML files, and that's it. Think of it like printing a document: once it's printed, changing the original file doesn't update the printed copy. To get the new content onto the site, you have to "reprint" (rebuild) and replace what's on Hostinger.

① You publish content in Sanity Studio
② A developer runs npm run build — Astro fetches the latest Sanity content and generates new HTML files
③ Developer uploads ./dist/ to Hostinger public_html/
④ Only now is the updated content visible on medzo.com.au

Follow these steps every time content is updated in Sanity Studio:

Step 1 — Edit in Sanity Studio

  1. Go to https://medzo.sanity.studio and sign in with admin.
  2. Navigate to the relevant singleton (e.g. Home Page) or collection (e.g. Services).
  3. Make your edits in the Studio fields.
  4. Click Publish in the top-right corner. Do not leave documents in Draft state — drafts are not fetched at build time.

Step 2 — Rebuild the site locally

  1. Make sure your .env file has the correct PUBLIC_SANITY_PROJECT_ID and PUBLIC_SANITY_DATASET.
  2. Run npm run build in the project root. Astro will re-fetch all Sanity content and rebuild the static site into ./dist/.
  3. Optionally run npm run preview to verify the output locally before uploading.

Step 3 — Upload to Hostinger

  1. Log in to Hostinger hPanel.
  2. Open File Manager and navigate to public_html/.
  3. Delete the existing contents of public_html/ (or overwrite).
  4. Upload all files from your local ./dist/ folder into public_html/.
  5. Verify the live site at medzo.com.au.
ℹ️
Published content in Sanity is not live until the site is rebuilt and re-uploaded. The site is fully static — Sanity data is baked in at build time, not fetched in the browser.

Sanity — Adding a New Page

Adding a new page requires both a developer and (for CMS-managed content) a Sanity schema change. Follow every step in order — skipping steps causes type errors or broken builds.

Step 1 — Decide the content source

Will the page be edited by the team via Sanity, or is it a static page like Privacy/Terms?

  • CMS-managed (team edits content) → follow all steps below.
  • Static (dev edits code only) → skip steps 2–4; add content to src/lib/content/ and a type to src/types/ instead.

Step 2 — Add the Sanity document type (CMS pages only)

  1. Create a new schema file in sanity/schemas/ (e.g. pricingPage.ts) defining all the fields the page needs.
  2. Register it in the root schema index so Sanity picks it up.
  3. If it is a single page (not a collection), add it as a singleton in src/structure/index.ts so it appears correctly in the Studio sidebar.
  4. Run npx sanity schema deploy to push the schema to Sanity cloud.
  5. Run npx sanity typegen generate to regenerate TypeScript types from the new schema.

Step 3 — Add a TypeScript interface

  1. Add a typed interface for the new page's content shape in the appropriate file under src/types/ (e.g. add PricingContent to src/types/pages.ts).
  2. Every field in the Sanity schema should have a matching property in the TypeScript interface.

Step 4 — Add a data fetcher (CMS pages only)

  1. Create src/lib/api/pricingPage.ts (one file per page).
  2. Write a GROQ query using defineQuery() that selects all the fields the page needs.
  3. Export an async fetcher function that calls sanityClient.fetch() with that query.
import { defineQuery } from "groq";
import { sanityClient } from "./sanity";

export const PRICING_PAGE_QUERY = defineQuery(`
  *[_type == "pricingPage"][0]{ heading, plans[] { ... } }
`);

export async function getPricingPage() {
  return sanityClient.fetch(PRICING_PAGE_QUERY);
}

Step 5 — Build section components

  1. Create one .astro component per visual section in src/components/sections/.
  2. Each component must declare a typed Props interface at the top of its frontmatter.
  3. Keep each file under ~80 lines. Extract sub-components if needed.
  4. All text must come from props — no hardcoded strings in templates.
  5. All SVGs must come from icons["key"] — no inline SVG blocks.

Step 6 — Create the page file

  1. Create src/pages/pricing.astro (or the appropriate route).
  2. In the frontmatter, call the fetcher and destructure the data.
  3. In the template, import and compose the section components — no logic, no inline content.
  4. Pass title and description to <Layout /> for correct <head> metadata.
  5. Add the appropriate JSON-LD schema (breadcrumb, service, etc.) using builders from src/lib/content/schema.ts.

Step 7 — Wire up navigation & links

  1. If the page should appear in the top nav, add it via Sanity Studio → Site Settings → Navigation.
  2. If it belongs in the footer, add the link to src/lib/content/footer.ts.
  3. Check all existing pages for anywhere this page should be linked from.
  4. Run npx astro check — fix any type errors before continuing.

Step 8 — Enter content in Sanity Studio

  1. Open Sanity Studio, find the new document type, and fill in all fields.
  2. Click Publish.

Step 9 — Build, verify, and deploy

  1. Run npm run build — confirm no errors.
  2. Run npm run preview and navigate to the new page.
  3. Keyboard-navigate the page and run a Lighthouse accessibility audit.
  4. Check that the sitemap includes the new URL (open ./dist/sitemap-*.xml).
  5. Upload ./dist/ to Hostinger public_html/.
  6. Verify the live page at medzo.com.au/your-new-page.
✅
Quick checklist for new pages: typed interface in src/types/ → fetcher in src/lib/api/ → section components in src/components/sections/ → thin page file in src/pages/ → navigation wired → astro check passes → content published in Sanity → build + upload.

Web3Forms

The contact form on /contact submits to Web3Forms — a third-party form submission service that forwards enquiries to a nominated email address without requiring a backend server.

ℹ️
Login: The Web3Forms account is accessed at web3forms.com using info. This account holds the access key and controls where form submissions are delivered.

How it works

DetailValue
Submission endpoint https://api.web3forms.com/submit
Access key PUBLIC_WEB3FORMS_KEY env variable — injected as a hidden <input name="access_key">
Callback (redirect) URL https://medzo.com.au/contact?success=1 — Web3Forms redirects back here after a successful submission
Success detection On page load the script checks for ?success=1 in the URL, hides the form, and shows the success message. The query param is then removed from the URL silently.
Email subject "Practice Management Enquiry" — set as a hidden <input name="subject">, value comes from src/lib/content/contact.ts → defaultSubject
Spam protection Honeypot botcheck — a hidden checkbox (name="botcheck") that is invisible to real users but triggers Web3Forms' spam filter if a bot fills it in
Re-submission guard Client-side 60-second cooldown after a successful send prevents accidental double-submissions

Submission flow

  1. User fills in the form and clicks Send message.
  2. The form data is sent via fetch() as JSON to https://api.web3forms.com/submit.
  3. Web3Forms validates the access key and forwards the submission as an email to the address registered under the account (info).
  4. On success, the form is hidden and the inline success message is shown — no page navigation occurs.
  5. If the JS fetch fails (e.g. network error), the form falls back to a standard HTML POST to the same endpoint, which then redirects back to /contact?success=1 where the success state is shown.

Changing the destination email

The email address that receives form submissions is configured inside the Web3Forms account — it is not set in the codebase. To change it:

  1. Log in to web3forms.com with info.
  2. Find the access key associated with this project.
  3. Update the notification email address in the key settings.

Rotating the access key

If the access key needs to be replaced (e.g. key is compromised):

  1. Log in to Web3Forms and generate a new access key.
  2. Update PUBLIC_WEB3FORMS_KEY in the local .env file.
  3. Rebuild the site with npm run build — the new key is baked into the form's hidden input at build time.
  4. Upload the new ./dist/ to Hostinger.
⚠️
The access key is prefixed PUBLIC_ and is visible in the built HTML source. This is intentional — Web3Forms keys are domain-scoped and designed to be public. Submissions from unauthorised domains are rejected by Web3Forms automatically.

Changing the email subject line

The subject of every notification email is set in code, not in Web3Forms. To change it, edit the defaultSubject field in src/lib/content/contact.ts, then rebuild and redeploy. 

// src/lib/content/contact.ts
defaultSubject: "Practice Management Enquiry",  // <-- edit this

Troubleshooting

Common issues and how to resolve them.

Build & development

Build fails with "Cannot find module" or import errors

Dependencies are missing or outdated after a pull.

npm install

Build fails with TypeScript type errors

A component prop type doesn't match what's being passed, or a Sanity field was renamed. 

# Run the type checker to see all errors at once
npx astro check

Fix each reported mismatch. If a Sanity schema field was changed, also run npx sanity typegen generate to regenerate the types.

Dev server starts but pages are blank or show no content

The .env file is missing or the Sanity variables are wrong.

  • Confirm .env exists in the project root (not inside src/).
  • Check PUBLIC_SANITY_PROJECT_ID matches the value in the Sanity dashboard under Project Settings.
  • Restart the dev server after editing .env — it is only read on startup.

"astro check" reports broken links or missing pages

An internal link points to a page that doesn't exist.

  • Either create the missing page or update the link in the relevant content file in src/lib/content/.
  • All internal links must use root-relative paths (e.g. /about, not ../about).

Sanity & content

Content updated in Sanity but not showing on the live site

The site is static — Sanity content is baked in at build time, not fetched live.

  • Make sure the document is Published in Sanity Studio, not just saved as a Draft.
  • Rebuild the site with npm run build and re-upload ./dist/ to Hostinger.

Images uploaded to Sanity are not displaying

  • Confirm the image asset was fully uploaded in Studio (no upload spinner visible).
  • Publish the document — draft images are not accessible via the CDN.
  • Check that cdn.sanity.io is in the remotePatterns list in astro.config.mjs — it is by default, so this only breaks if the config was changed.
  • Rebuild and redeploy.

New service added in Sanity but no page created at /services/[slug]

  • Make sure the service document has a slug field set in Studio.
  • Publish the document.
  • Rebuild — Astro generates the dynamic /services/[slug] route at build time using the slugs returned by the GROQ query.

Contact form

Form submissions are not arriving by email

  • Check the spam/junk folder for the destination email address.
  • Log in to Web3Forms (info) and check the submission log — if submissions appear there, the issue is email delivery, not the form.
  • Verify PUBLIC_WEB3FORMS_KEY in .env matches the active key in the Web3Forms account. If the key was rotated, rebuild and redeploy.
  • Open browser DevTools → Network tab, submit the form, and look for the request to api.web3forms.com/submit. A non-200 response indicates an invalid key or a blocked domain.

Form shows success but no email received

  • The form submitted successfully to Web3Forms but email delivery failed. Check spam folders first.
  • Log in to Web3Forms and verify the notification email address on the access key is correct.
  • Web3Forms has a free-tier submission limit — check if the monthly limit has been reached in the account dashboard.

Deployment

Live site shows old content after uploading to Hostinger

  • Hard-refresh the browser (Ctrl + Shift + R / Cmd + Shift + R) to bypass the browser cache.
  • Confirm all files from ./dist/ were uploaded, not just a subfolder.
  • Check that old files were deleted or overwritten in public_html/ before uploading — stale files can persist if not removed.

404 errors on all pages after uploading to Hostinger

  • Files were likely uploaded into a subfolder inside public_html/ rather than directly into it. The index.html must sit at the root of public_html/.
  • Verify via Hostinger File Manager that public_html/index.html exists.

Known Limitations

These are current gaps in the project that the support team should be aware of. None of them break the site — but they affect how certain tasks must be done.

① Sanity content changes require a manual redeploy

Publishing in Sanity Studio does not update the live site. The site is static — content is baked in at build time. Every Sanity change requires a developer to rebuild and re-upload to Hostinger before it goes live.

Future fix: Configure a Sanity webhook that triggers an automated build pipeline (e.g. GitHub Actions) on every publish. This would eliminate the manual step entirely.

② No automated CI/CD pipeline

There is no automated build or deployment when code is pushed to GitHub. Every deploy — whether a content change or a code change — is a fully manual process: build locally, upload to Hostinger via File Manager.

Future fix: Set up GitHub Actions to build on push to main and auto-upload to Hostinger via FTP. Or migrate hosting to Vercel/Netlify which handle this natively.

③ No staging environment

There is only one environment — production at medzo.com.au. Changes cannot be previewed on a live URL before going public. The only way to verify before deploying is to run npm run preview locally.

Future fix: Create a separate Hostinger subdomain (e.g. staging.medzo.com.au) or use a free Netlify/Vercel deployment as a preview environment.

④ No Sanity draft preview

There is no way to preview what a Sanity draft document looks like on the real site without publishing it first. Draft content is invisible until published and the site is rebuilt.

Future fix: Implement Sanity's Visual Editing or draft mode with an Astro SSR preview route that bypasses the CDN and reads unpublished drafts.

⑤ Web3Forms free tier submission limit

The Web3Forms free plan allows 250 contact form submissions per month. Submissions beyond this limit will silently fail — no email is delivered and no error is shown to the user.

Fix: Monitor submission count in the Web3Forms dashboard (login: info). Upgrade to a paid plan if the limit is regularly reached.

⑥ No automated tests

There are no unit tests, integration tests, or end-to-end tests. The only automated check is npx astro check for TypeScript type errors. UI regressions can only be caught by manually reviewing the site after each deploy.

Future fix: Add Playwright end-to-end tests for critical flows (home page load, contact form submission, service page navigation).

⑦ No error monitoring

There is no Sentry, LogRocket, or equivalent error tracking on the live site. If a JavaScript error occurs or the contact form breaks, there is no alert — it is only discovered when a user reports it or someone manually checks the site.

Future fix: Add Sentry (free tier) or a simple error boundary that logs to a monitoring service.

⑧ Sanity images are publicly accessible

All images uploaded to Sanity are served from cdn.sanity.io and are publicly accessible to anyone who has the URL — there is no private asset support on the current plan.

Rule: Do not upload sensitive, confidential, or private documents or images via Sanity Studio.

Access environment variables in code via import.meta.env.PUBLIC_SANITY_PROJECT_ID. Never hard-code project IDs or dataset names in source files.
